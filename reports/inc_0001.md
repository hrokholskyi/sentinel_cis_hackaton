## 4. Assessment

- Three beneficiaries added by the same user on the same minute, dormant for 213 days, all woken up at 02:00.
- Phase A: AED 4,500, just under the soft minimum AED 5,000, so `off_hours_amount` and `first_payment_above_limit` stay silent. This creates "prior payments".
- Phase B: AED 11,750 (2.6 x the warm-up) to the same three, every 2 seconds.
- No invoice, payroll or loan basis exists for any of them; the client's normal payments all carry one.
- This is a stolen-key or insider pattern, not a client mistake.

Why not the other verdicts:

- `release`: the breaker re-check needs an approved unused basis of the same amount; none exists, so nothing could pass, and the evidence points to fraud.
- `hold_until_morning` / `contact_client`: holds would stay, but AED 27,000 has already left and the key is likely compromised; this needs bank security (recall, key rotation), not only a client call.

## 6. Why layer 1 had no specific rule

- The six original rules only look at amount (soft minimum, 1.5 x prior max), time, count and sum.
- Nothing looked at beneficiary age, dormancy or the missing basis. The first-payment rule has an amount floor of AED 5,000, so a dormant beneficiary could be "warmed up" below it.
- After the warm-up, `amount_above_typical` and `first_payment_above_limit` see "prior payments" and only `burst_count_5m` stopped the run, after 6 executed.

### Code paths that reach the bank payout (graphify `graphify-out/graph.json`)

The bank `POST /payouts` (`bank/app.py:payout`) is reached only over HTTP from `breaker/app.py:forward()`. Callers of `forward()`:

| Path | Caller | Business check before `forward()` |
|---|---|---|
| 1 | `payout()` -> no violation (`decided_by=breaker`) | all `rules/*.sql` (layer 1) |
| 2 | `payout()` -> soft only -> `decide_soft()` -> Jev release (`jev`) | rules, then `release_gate()` -> `incidents.recheck(basis_required=True)` |
| 3 | `payout()` -> key in probe (`probe`) | rules, then `engine.probe_gate()` (prior payments, AED 1,000 cap) |
| 4 | `verdict()` -> `_release()` (`verdict`) | `incidents.recheck()` (prior payment + approved unused basis, same amount) |
| 5 | `release_hold()` (admin token, `admin`) | human decision on one hold |

Paths 2-4 already require a prior payment and/or an approved basis.
Path 1 is the only automatic path that sent money for a dormant beneficiary without a basis, and every payout request passes layer 1 before any path is chosen.
So the choke point is layer 1 itself: the new rule runs on every `POST /payouts` request, before paths 1-3, and its holds can only leave through paths 4-5, which keep their own checks. No code change was needed.

## 7. New rule

`rules/07_dormant_beneficiary_no_basis.sql`, level `hard`: violated when the beneficiary was approved more than 30 days ago, has no bank payment older than 24 hours (dormant, or woken up within the last day) and the payment does not name an approved, unused basis of this client for this beneficiary with exactly the payment amount, that no other pending, released or executed payment carries (the current payment is already inserted as `pending`, so it counts as 1).
It uses `julianday()` arithmetic, so the webhook window stays the 1 hour default.
